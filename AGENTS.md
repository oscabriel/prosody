# Prosody

One self-hosted app for the whole route a book travels: wanting it, fetching it, shelving it, syncing its audiobook to its ebook, and reading or listening. It does the work of a book grabber, an audiobook server, an ebook reader and an aligner in one. the indexer and the download client stay outside it.

## State

Steps 1 and 2 are done: each book with both editions is paired, aligned by the press with our own aligner (`packages/aligner`), spot-checked by ear, kept as a reading copy in the copies folder, and opens at `/read/<work>`, where the audio follows the text and one place per book is kept across devices. The Api serves the built app at `https://read.example.com`, to your own devices only. The app installs on the phone and opens there with no network, shows the book on the lock screen and answers its buttons, keeps your place on the device while offline, and keeps a whole book on the device when asked. The shelf opens on the nightstand: what you are reading now. A book with one edition opens too: the press makes a reading copy of an EPUB alone, to read with no player, and of an audiobook alone, to hear by its chapters, and the shelf says which kind each book is. Every copy the press makes has the book's cover, on the shelf, in the room and on the lock screen. Step 3 is done: at the desk you want a book by its title and author, the model searches the indexer for it and offers what it finds as it comes, and catalogues its work as Open Library and Audnexus know it. You grab one of the offers; the download client downloads it, the press watches it, copies its edition into the library when it has come, and the book pairs and aligns on its own. The desk shows each grab from its download to the end of its sharing, and lets you resume a stall, abandon a grab, and release a payload once it has shared its 72 hours. `pnpm check` must pass before a commit. The next work is step 4: PDFs and comics.

- `pnpm check` formats, lints, typechecks and tests. `pnpm run deploy` deploys; `pnpm deploy` is a different, built-in pnpm command.
- `packages/domain` imports only `effect` and `@alchemy.run/domain`. The linter enforces it.
- The Api serves the built app: `/`, `/read/<work>`, the hashed files under `/assets/`, which browsers keep for a year, and the files at the top of the build (`/worker.js`, `/manifest.webmanifest`, the icons), which they never keep. `pnpm run deploy` and `pnpm run plan` build `packages/web` first; the build is the Api's base image, `PageImage` (`packages/web/Dockerfile`), tagged with a fingerprint of the build and the Dockerfile so a change to either moves the Api. The dev server (`pnpm --filter @prosody/web dev`) still runs at `https://prosody.example.com`, behind the same sign-in.
- Sign-in is Tailscale's. Before every request to `read.example.com` or `prosody.example.com`, Caddy asks the Api's `/auth` about the address it came from (`X-Prosody-Peer`), and the Api asks tailscaled whether that is an untagged machine of the host's own owner. `/auth` also refuses a request made by another site's page (its `Origin` or `Sec-Fetch-Site`), since the tailnet vouches for a machine, not for what runs on it. Caddy copies the machine's name onto the request as `X-Prosody-Device`. The reader's Api (the `Session` middleware, which gives `decide` the `Device`) and `/copies` refuse a request without it with `SignedOut`. Anything on the host that calls the relay directly can name any device; nothing off the host can reach the relay. The press's `/press` is still refused to anything that comes through the relay.
- The Api reaches tailscaled through its socket, in `/var/run/tailscale`, which it mounts. It runs as `nobody`: tailscaled takes settings from root and from its operator (you, uid 1000), and only answers anyone else. A mount cannot limit a socket, so keep that `USER`. systemd makes the folder anew whenever tailscaled starts; the Api's healthcheck then fails and swarm replaces it. `docker service update --force` on the Api does the same by hand.
- `.alchemy/` is Alchemy's record of what is deployed. Never delete it while the stack is up.
- The press runs in its own base image, `packages/press/image/Dockerfile`, as uid 1000. Bump `PressImage`'s tag in `Press.ts` whenever the Dockerfile changes, or the press keeps the old image.
- Alchemy runs a service's setup on the host when it plans a deploy. Anything that touches the container's own files or mounts goes inside `host.run`.
- Alchemy 2.0.0-beta.87 misses a change to a service's code alone when the service's settings depend on other resources. The Api and the press carry `PROSODY_SOURCE`, a fingerprint of the source (`packages/server/src/Source.ts`), so code changes deploy; give any new service the same.
- A deploy replaces each service stop-first, so for a few seconds the Api has no task, and its address (`prosody-api`) then reaches the calling container itself: a call from the press is answered by the press's own server. Bun keeps such a connection and would send every later call down it, long after the Api is back, so the press calls the model with a new connection each time (`keepalive: false` in `Press.ts`). Anything new that calls another service from Bun needs the same.
- Policies act only on new events, never on history. A rule that must also cover what is already recorded needs another trigger: the press reports pairs, and editions alone, on every walk for this reason.
- Bump a view's `version` whenever what it computes changes, so it is rebuilt from the history. On Alchemy 2.0.0-beta.87's Effect Cluster host that only works for a view keyed by its one aggregate (`Place`), which is rebuilt in place. A view fed through `keyOf` (`Shelf`, `Nightstand`) is backfilled, and the backfill finds no history: its directory listing sends `after` as `null`, which matches nothing. Such a view added to a running stack, or bumped, starts empty. `Nightstand` did; it fills as books are opened. Giving such a view another source without a bump does work on this host (the backfill's "changed" answer is ignored, and new instances route live): `Shelf` reads `Copy` that way, which is fine only because every `Copy` event is newer than the change.
- The service worker is `packages/web/src/Worker.ts`, built apart from the page, with none of its plugins, by the `worker` plugin in `vite.config.ts`, which writes in the paths of the page, the lock screen's icon and every built file so it keeps them all when it installs. It answers a load of the app's own pages (`/` and `/read/<work>`) from the network and, when the network fails or has not begun to answer in three seconds, from the kept page; a built file from the device; a reading copy's file the same way as a page, from a kept copy; and `?kept` audio from a kept copy's pieces. Any other address goes to the network untouched. Only a build registers it; the dev server has none.
- Offline is queued intent. Your place in each work is kept on the device (`localStorage`, `prosody:places`) with the command id that carries it, sent with that id whenever the model can be reached, and waits no longer once the model answers, kept or `StalePlace`. A lost answer marks the page offline, and it asks the server (`HEAD /`) every five seconds until it answers; the browser's `online` event also brings it back. An open book waits three seconds for the model's word on your place, then opens at the device's own.
- "Keep on this device" puts a work's copy in the Cache API, one cache per work (`copy-<work>`, see `OnDevice.ts`): its contents, timeline, cover, pages and pictures, the audio in 8 MiB pieces as the Api sent them, and a record written last. A copy with audio counts as big as its audio; a text alone as big as what the cache holds for it (Caddy compresses text, so a response carries no length to add up). A copy without its record is not whole, and keeping it again fetches only what is missing. A room plays a kept copy from its own address, `<audio>?kept`, chosen as the room opens: a media element fails when one address gives it bytes from both the network and the device.
- The nightstand is `OpenBook` (sent once a room's book has opened, and again when the connection comes back until the model answers it), `FinishBook` and `SetAside` on `Reading`, and the `Nightstand` view, keyed like the shelf. `OpenBook` puts a finished book back on the nightstand, so it is sent only for an open you made: finishing a book or setting it aside puts the shelf's address in place of the room's, or reloading the room, or going back to it, would open it again. A `Reading` stored before stages existed decodes as `unopened`, and goes on the nightstand when it is next opened.
- The lock screen shows the book, its author, the chapter and its cover (the app's icon for a copy with none), and its play, pause, skip and seek buttons move the audio element itself (`Player.ts`, `LockScreen.ts`). A text alone has no player and puts nothing there.
- A book with one edition has a `Copy` (Reading): the press reports the edition alone on every walk (`CopyEdition`; the same file at the same size again records nothing), and the `ReadingCopy` policy asks the press (the `Copier`) to make its copy, unless the `Work` has both editions by now. That check matters: a failing mount can hide one half of a pair for a walk, and the Work never forgets an edition, so a synced copy is never replaced by a copy of one half. The press answers `RecordCopy` or `RecordCopyFailed`, and sends the answer again for five minutes, through a deploy that replaces the Api. There is no deadline: a copy takes a second or two and waits on disk until it is answered. A failed copy stays failed until its file is replaced by one of another size (another name is `AlreadyShelved`), or you send `RemakeCopy`: the shelf links a book whose copy failed to its room, which says why and offers to make it again. A text with no sentences to read (pictures alone, or scanned pages) fails.
- A place is a sentence, or, in a work with its audio alone, a time in seconds (`Position`: `sentence` and `time`, each `null` when it is not that kind). A place kept before there were times decodes with `time: null`. A book heard alone and paired later opens at the sentence read at its time. In audio alone the place is kept every fifteen seconds while it plays, on pause, and whenever the audio is moved while paused (a chapter, a skip, the lock screen).
- The desk is `/desk`, a tool with the plain treatment: the same tokens, a sans face, no leaf. A book you want is a `Want` (Acquisition), keyed by the work it will be; the desk makes that work id (`w-` and twelve random hex digits) as you want it. A `WorkId` is `w-` and lower-case letters or digits, so the Api refuses any other a device sends, and a room's address with anything else is not found. `WantBook` starts the first search, `SearchAgain` another, `WithdrawWant` takes it off the desk. The `ReleaseSearch` policy asks the `Indexer` and answers `OfferReleases` (the ten most shared audiobooks and the ten most shared ebooks, each named as the indexer grabs it: `<indexer id>_<guid>`) or `RecordSearchFailed` with the reason; an answer to an older search, or to a book withdrawn, records nothing. A failed search waits for you to search again; nothing retries it. The `Wanted` view, keyed like the shelf, is what the desk watches, so offers appear as they come. No policy grabs anything.
- The Indexer is the indexer (the indexer's adapter): one `GET /api/v1/search` with its API key, in the indexer's audiobook and ebook categories. Prosody holds the indexer's address and key only, as `INDEXER_URL` (no slash at the end) and `INDEXER_API_KEY` in `.env`, which git ignores; never a source login. the indexer down or refusing the key is a failed search the desk shows, not an error.
- Alchemy binds a `Config` value to whatever was being built when it was read, and the model's Layer is built by the Api, not the runner, which builds it again at run time from its own environment. So the runner pool (`Runners` in `ProsodyLive.ts`) reads the indexer's and the download client's settings as it is declared, and the deploy gives them to the runner alone; the adapters read them again only as they run, so the Api never has them. The press reads the download client's as it is built, for its watch. A setting the runner's policies need must be read there the same way, or the runner fails as it starts. `docker service inspect` shows them.
- Wanting a book catalogues its work: the `Cataloguing` policy asks `Metadata` once (`OpenLibraryMetadata.ts`: Open Library for the title, author, year and work; Audible's catalogue to find the audiobook's ASIN, since Audnexus has no search; Audnexus for its narrators, length and chapters) and sends `CatalogueWork` with no shelfmark and that description. Open Library has 8 seconds: a policy that dies within the platform's 10 second backstop is run again, one that dies later is not; the audiobook's lookups have 30 seconds and give no audiobook when they fail. Open Library may complete the names you gave (weir is Andy Weir), never replace them (Homer stays Homer). None of them needs an account, and they are sent a title and an author only. A wanted work is not on the shelf until it is shelved. A work the press found has no description, as every work catalogued before had.
- Grabbing is yours alone: no policy sends `GrabRelease`. It goes to the `Want`, which knows what the latest search offered, and refuses anything else (`ReleaseNotOffered`; a desk kept before grabs shows its old offers as "search again to grab it"). Each release a want grabs is a `Grab` (Acquisition), keyed `<work>.<n>`, which the `Grabbing` policy opens; the `Downloading` policy hands it to `Downloads`, and a download that can't be started is a stall with the reason. The press reports how each download goes: `RecordProgress`, `RecordStall`, `RecordPayloadArrived` and the command that records the hours, each recorded only when it is news. `ResumeGrab`, for any grab still downloading, starts its download again and asks the source for peers, or adds it again if the download client does not have it (removed there by hand, or never added); progress also ends a stall. `AbandonGrab` only stops Prosody watching: the download and what came of it stay in the download client, and the want keeps the release as grabbed, so it cannot be grabbed again. `ReleasePayload` is refused with `StillObligated` and the hours owed until the download client has shared the payload 72 hours (the source's rule; the desk shows the day, 30 days from its arrival, they are owed by); then the `Releasing` policy removes it from the download client's list with `deleteFiles=false`. Those hours are the download client's own count of the time, which counts on while the source refuses its announces, so the desk asks you to check the source counts them before you release. Nothing in Prosody ever deletes or moves a payload.
- Downloads is the download client (the downloads adapter, the downloads adapter), signed in afresh for each use with `DOWNLOADS_URL`, `DOWNLOADS_USERNAME` and `DOWNLOADS_PASSWORD` from `.env`. A grab's download file is fetched through the indexer by the release's `link` (the indexer's download link with its API key taken out, kept on every offer since this part) and added under the `books` category, tagged with the grab's id: the tag is how the press finds a grab's download again. The press watches every minute (`Watch.ts`): a download still coming is stalled when nothing has come for half an hour, when the download client stopped it, or when it reports an error or missing files; one that has all come names its payload, its file or folder inside the books downloads.
- Shelving: on `PayloadArrived`, the `Shelving` policy names the work's folder from its catalogued title and author (`shelfmarkOf`, which keeps a name to one folder), claims it (`ShelfmarkClaim`, keyed by the shelfmark: the first work to claim a folder holds it, and every later claim is told whose it is with `ShelfmarkTaken`), and asks `Stacks`, the press (`/shelve`), to copy the edition in. A folder another work holds takes the edition for that work, so an audiobook grabbed for an ebook already on the shelf pairs with it. The press copies, never moves: it checks the library and the downloads answer within 8 seconds and the library is not empty, takes the one `.epub` or `.m4b` in the payload, copies it under a hidden `.part` name and renames it `<Title> - <Author>.<ext>`, so a walk never finds half a file, and answers `RecordShelved`, then walks the library at once. A library or downloads folder that does not answer, or a copy that fails, is `RecordNotShelved` with the reason, and the payload goes back in line five minutes later, so the ones behind it go on; a payload with no such file, or more than one, a folder that has that edition already, or a shelfmark that is not an author's folder and a title's, is `RecordNotShelved` for good. The press mounts the library writable, as its one writer, and the books downloads read-only.
- The walk claims every folder it finds for the work named after it, `sha256(author/title)`, and reports the folder under whichever work holds it. That is how a folder shelved for a work you wanted keeps that work's id. Such a work, catalogued with no shelfmark, is catalogued again when the walk first finds it, so it appears on the shelf. `CorrectTitle` corrects a wanted work's title and author until it is on the shelf (`OnTheShelf` after): its folder is named for them. A work stored before works kept their names has none; shelving then asks the catalogues again, for the names you gave, and names its folder as they do.
- `.pending` in the copies folder is the press's queue, `<work>.json` for a pair to align and `<work>.<attempt>.copy.json` for an edition to copy, one at a time in the order asked, so a copy can wait behind an alignment; and `<grab>.shelve.json` for a payload to shelve, in a line of its own, so shelving never waits behind an alignment. A request stays there until its answer is sent. After a restart they are taken in name order, so a work's copy runs before its pair, which replaces it.
- The Api serves the reading copies read-only at `/copies/<work>/`: `contents.json`, `timeline.json`, `cover.jpg`, `text/` and `audio/`. `contents.json` says what the copy is: the audio to play (`null` for a text alone), the pages (none for an audio alone), the audio's chapters (an audio alone's, from the file, by ffprobe) and the cover. Only a pair has a timeline. A copy without `contents.json` is unfinished or was made before the reading room; `RealignNarration` or `RemakeCopy` makes it again.
- The press makes the cover with ffmpeg, as `cover.jpg` no taller than 800 pixels, from the picture the EPUB names, or else the one the audio file carries. A copy made before covers has none until it is made again: `RealignNarration` each pair once. The shelf draws a plain binding with the title's first letter under every cover, so a missing one shows that.
- A page's title in the contents is what the EPUB's own table of contents (its NCX) calls it, or else its first heading. Text the narrator would not read (a cover, the contents, an index) is left out of a text alone as well, so both kinds of copy mark the same pages.
- The aligner runs NVIDIA's Parakeet CTC 0.6B (int8 ONNX) through `@huggingface/transformers`, and Whisper base.en for the spot check. The press image downloads both at pinned revisions into `/models` and runs offline; the bundle leaves `@huggingface/transformers` external, installed in the image's `/app`. Changing either model means a new image tag.
- What the model heard is kept beside each reading copy as `heard-<size>.emissions`, so a realign never listens again. Change the emissions format and those files must be ignored or rebuilt.
- `packages/aligner/bench` runs the aligner on saved emissions, outside the press: `run.ts` end to end, `align.ts` to try costs, `reorder.ts` and `unread.ts` for audio out of order or text not read.

## Before using an API

- Alchemy's domain framework (`@alchemy.run/domain`) and its Effect Cluster host are weeks old. Read the installed `node_modules` source, and Alchemy's own docs, before writing against them. The code in the plan is a sketch that was never run.
- Read `node_modules/effect/AGENTS.md` before writing Effect code. Effect 4 differs from what you remember.
- Alchemy stays on the newest release.

## The checks

`pnpm check` is the gate: format, type-aware lint, typecheck, tests. Warnings fail it. `pnpm fix` applies the safe lint fixes and formats.

- One TypeScript everywhere: `typescript` and `tsrs` are both 7.1 beta, and Oxlint runs its type-aware rules on tsrs, Oxc's Rust port of the checker, which it picks over `oxlint-tsgolint` when both are installed. `prepare` patches both with Effect's rules (`effect-tsgo patch --oxlint --tsrs`), so plain `oxlint` in the scripts, the editor and the agents' hook all lint the same way. Move `typescript`, `tsrs` and `@effect/tsgo` together, to versions `@effect/tsgo`'s README lists as supported; an unpatched tsrs fails with `unknown rule: effecttsgo/...`.

- The lint has three layers: Ultracite's presets, Effect's own rules (`@effect/tsgo`, patched in by `prepare`), and anti-slop, copied into `tools/oxlint/anti-slop` (its `UPSTREAM.md` names the commit). The anti-slop copy is ours: change a rule there rather than turning it off file by file.
- Effect's `recommended` preset, plus eleven of its rules beyond it, named in `oxlint.config.ts`: inside an Effect, use Effect's `Config`, `Clock`, `Schema`, `HttpClient`, `Console` and `Random` rather than the globals, and say what an error becomes, how much runs at once (`concurrency`) and where layers are provided. `strict-effect-provide` is off only in the entry points listed there. The rest of Effect's rules are style, for library authors, or for the browser, and stay off.
- Where Effect's style and Ultracite's disagree, Effect's wins: barrel imports (`import { Schema } from "effect"`), `Array<A>`, PascalCase module files. Each exception is named in `oxlint.config.ts`.
- Before using an Effect module that Effect marks unstable, add it to `allowedUnstableApis` in `tsconfig.base.json`.
- Not turned on: anti-slop's code-smell rules (they warn) and its model-judged and diff rules (they send source to a paid model on every run).
- For how to shape Effect services, use the `effect-program-design` skill. It is anti-slop's policy, the one its Effect rules encode, installed globally and adapted to Effect 4.1.4 (its `LOCAL-CHANGES.md` lists how). Where it still disagrees with `node_modules/effect/AGENTS.md`, Effect's wins.
- `.claude/settings.json` runs `oxlint --fix` and `oxfmt` on every file an agent edits.
